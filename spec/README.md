**변경 이력**

- 2026-10-03: 파일 목록에서 가벼움 기준에 prefix(PERF)를 함께 적었다
- 2026-10-03: 최종 리뷰 반영 — 체크리스트에 올리는 곳(REL은 Windows만)과 OS 효과의 자동 테스트 범위를 적고, 테스트 참조 규칙과 "v1.4와 다른 점" 표를 더했다

## 이 폴더가 기준이다

`spec/`은 v2.0이 지금 실제로 어떻게 동작해야 하는지를 정하는 **기준 문서**다. 코드와 이 폴더의 내용이 다르면 코드가 틀린 것이다.

`docs/superpowers/specs/`는 설계 시점의 기록으로 남겨 둔다. 바뀐 결정은 설계 문서가 아니라 여기 반영한다.

## 요구사항 형식

요구사항 하나는 이렇게 쓴다. `조건`과 `동작`은 필요할 때만 쓰고, `결과`와 `확인`은 반드시 쓴다.

    ### TASK-09 이미 끝낸 일을 다시 끝낸 일로 지정하면 아무것도 바뀌지 않는다
    - 조건: 상태 `done`, 끝낸 시각 `2026-10-03T09:00:00+09:00`
    - 동작: 상태를 `done`으로 지정한다
    - 결과: 끝낸 시각은 그대로 `2026-10-03T09:00:00+09:00`이고, 저장도 화면 갱신도 일어나지 않는다
    - 확인: 자동 테스트

`확인` 값은 둘 중 하나다.
- **자동 테스트**: 테스트 코드로 확인한다. 테스트가 이 ID를 가리켜야 한다.
- **직접 확인**: 사람이 실제 기기에서 눈으로 보고 확인한다. `spec/checklists/`에 같은 ID로 올려야 한다.

직접 확인 항목을 올리는 곳은 이렇다. `pnpm spec:check`가 빠진 곳을 알려 준다.
- 공통 행동(`spec/behavior/`, `spec/00-principles.md`): `windows.md`와 `macos.md` 양쪽
- `WIN`: `windows.md`만, `MAC`: `macos.md`만
- `REL`: `windows.md`만. 출시 확인은 PM이 Windows 체크리스트로 진행하기 때문이다(REL-04)

OS에 실제 효과가 있는 자동 테스트 항목은 port 호출까지만 자동으로 확인하고, 실제 효과는 체크리스트의 '기본 동작 훑어보기' 줄에서 본다. 예를 들어 WND-09의 자동 테스트는 📌를 누르면 `WindowController`에 맨 위 고정을 요청하는지까지 보고, 창이 실제로 다른 창 위에 뜨는지는 그 줄에서 본다.

## 테스트에서 ID를 쓰는 법

- TypeScript: 테스트 이름 앞에 ID를 적는다. 예: `it('TASK-09 이미 끝낸 일을 다시 끝낸 일로 지정하면 아무것도 바뀌지 않는다', ...)`.
- Rust: 테스트 함수 위 주석에 ID를 적는다. 예:
  ```rust
  /// STORE-02 저장은 원본을 깨뜨리지 않는다
  #[test]
  fn keeps_original_file_on_write_failure() { /* ... */ }
  ```
- `pnpm spec:check`가 참조로 세는 곳은 `src/**/*.test.ts`, `src-tauri/src/**/*.rs`, `src-tauri/tests/**/*.rs`, `.github/workflows/*.yml`이다. `src-tauri/src/`에서는 3줄 안에 `#[test]`가 오는 `//`·`///` 주석의 ID만 센다. TypeScript에서 `.skip(`이나 `.todo(`가 있는 줄의 ID는 세지 않는다. workflow는 출시·성능 검사 단계 이름에 ID를 적는다(예: REL-05, PERF-05).

## v1.4와 다른 점

v1.4와 일부러 다르게 정한 것이다. v1.4를 역으로 spec화할 때 이 표에 없는 차이가 보이면 spec이나 이 표 중 하나가 틀린 것이다.

| 바뀐 것 | v1.4 | v2.0 | spec |
|---|---|---|---|
| 시각 기록 | 한국 표준시 `yyyy-MM-dd HH:mm:ss` | 기록하는 순간의 PC 시간대를 포함한 ISO 8601 | STORE-05 |
| `tasks.json` 모양 | 할 일 배열 | `{ "version": 2, "tasks": [...] }` | STORE-04 |
| v1.4 파일 | 해당 없음 | 켤 때 백업을 만들고 한 번 변환한다 | STORE-12 |
| `settings.json`의 틀린 항목 | 하나라도 틀리면 모든 항목이 기본값 | 틀린 항목만 기본값 | STORE-15 |
| `settings.json`의 모르는 항목 | 저장할 때 버린다 | 저장할 때 남긴다 | STORE-15 |
| 맨 앞 BOM | .NET이 저절로 건너뛰었다(규칙은 없었다) | 규칙으로 정했다. 결과는 v1.4와 같다 | STORE-19 |
| 화면 밖 위치 판단 | 모든 모니터를 감싼 사각형 하나로 판단 | 모니터마다 판단 | WND-08 |
| 투명도 반올림 | .5는 짝수 쪽으로(14.5 → 14%) | .5는 올린다(14.5 → 15%) | WND-11 |
| 같은 상태로 지정 | 저장한다 | 변경 없음, 저장하지 않는다 | TASK-09, TASK-10 |
| 같은 제목으로 이름 바꾸기 | 저장한다 | 변경 없음, 저장하지 않는다 | TASK-11 |
| 자동 실행 실패 | 대화 상자 | 위젯 안내 줄. 다시 바꾸는 데 성공하거나 다시 켜면 사라진다 | START-05 |
| 안내 줄 | 저장 실패만, 한 줄 | 한 번에 하나를 우선순위로 고르고, 두 줄까지 줄바꿈된다. 업데이트 실패 옆에 다시 시도 버튼, `notice.newerFile` 옆에 업데이트 버튼 | START-09, UPD-07 |
| Windows 자동 실행 | Run 값만 본다 | 작업 관리자의 끈 표시(StartupApproved)도 보고, 끈 표시가 있어도 경로는 갱신한다. 제거하면 Run 값을 지운다 | WIN-03, WIN-04, WIN-05 |
| macOS | 없음 | 로그인 항목(SMAppService), 최소 macOS 13 | MAC-08 |
| Enter로 추가할 때 목록 기호 떼기 | 한다(v1.3 설계 문서에는 없다) | 그대로 한다. PM 확인용으로 적어 둔다 | INPUT-20 |
| 업데이트 | 없음 | 위젯 안에서 확인·설치 | UPD-01~09 |
| 다국어 | 한국어만 | 한국어, 영어, 독일어, 중국어 간체 | I18N-01~07 |

## 바꾸는 순서

동작을 바꾸려면 이 순서로 간다: spec 수정 → PM 승인 → 실패하는 테스트 → 구현 → 리팩터링.

문서마다 맨 위에 변경 이력을 두고, 바꿀 때마다 날짜와 내용을 한 줄 추가한다.

## ID 규칙

한 번 쓴 ID는 지우거나 다른 뜻으로 다시 쓰지 않는다. 요구사항을 없앨 때는 제목을 `(폐기)`로 바꾸고 남겨 둔다.

## 검사 명령

- `pnpm spec:check`: 요구사항 형식(모든 수준의 제목, 같은 항목 두 번), 없는 ID 참조, 체크리스트 누락(올려야 할 체크리스트마다)을 검사한다. 코드 블록 안은 검사하지 않는다.
- `pnpm spec:check:strict`: 위 검사에 더해 테스트가 없는 자동 테스트 항목도 실패로 본다. 출시 전에는 strict가 통과해야 한다.
