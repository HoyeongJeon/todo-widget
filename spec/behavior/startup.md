## 용어

**처음 실행**: 설정 파일 `settings.json`이 없는 상태에서 위젯을 켜는 것. 자동 실행을 켰는지 껐는지는 `settings.json`에 저장하지 않고, OS 자동 실행 등록 여부 자체를 기준으로 삼는다. OS별 등록 방법은 `spec/platform/`에 적는다.

**안내 줄**: 한 번에 안내 하나를 보여 주는 줄. 글이 길면 두 줄까지 줄바꿈된다. 목록과 입력칸 사이에 있고(목록 화면 구성 4번), 알릴 일이 없으면 보이지 않는다.

## 요구사항

### START-01 위젯은 하나만 뜬다
- 조건: 위젯이 이미 떠 있다. 다른 창에 가려져 있을 수도 있다
- 동작: 위젯을 다시 실행한다
- 결과: 새 창을 만들지 않는다. 이미 떠 있는 위젯을 다른 창들 앞으로 가져오고, 맨 위 고정 상태(WND-09)는 그대로 둔다. 새로 실행한 프로세스는 할 일·설정 파일을 읽거나 쓰지 않고 바로 끝난다
- 확인: 직접 확인

### START-02 `settings.json`이 없으면 처음 실행이다
- 조건: `settings.json`이 없다
- 동작: 위젯을 켠다
- 결과: 지금 실행 파일 경로로 OS 자동 실행 등록을 켠다. 그리고 기본 설정으로 `settings.json`을 바로 만들어, 다음 실행부터는 처음 실행이 아니게 한다
- 확인: 자동 테스트

### START-03 처음 실행이 아니면 사용자의 자동 실행 선택을 지킨다
- 조건: `settings.json`이 있다
- 동작: 위젯을 켠다
- 결과: 자동 실행이 켜져 있으면 등록된 경로를 지금 실행 파일 경로로 갱신한다. 실행 파일을 옮겨도 자동 실행이 깨지지 않게 하기 위해서다. 꺼져 있으면 켜지 않는다. 사용자가 끈 자동 실행을 다시 켜지 않는다. 갱신하는 방법은 OS마다 다르다. Windows는 꺼진 표시가 있어도 남아 있는 등록 값의 경로를 갱신하되 꺼진 상태는 그대로 두고(WIN-03), macOS는 켜져 있으면 켤 때마다 지금 위치로 다시 등록한다(MAC-08)
- 확인: 자동 테스트

### START-04 ⋯ 메뉴의 자동 실행 체크는 실제 등록 상태를 보여 준다
- 동작: ⋯ 메뉴를 열고 `menu.autoStart`("컴퓨터 켤 때 자동 실행")를 누른다
- 결과: 메뉴를 열 때마다 OS 자동 실행 등록 여부를 읽어 체크 표시에 반영한다. 누르면 꺼져 있던 것은 지금 실행 파일 경로로 등록해 켜고, 켜져 있던 것은 등록을 지워 끈다. 그 뒤 등록 여부를 다시 읽어서 체크 표시를 맞춘다. 이미 꺼진 것을 다시 끄더라도 오류가 나지 않는다
- 확인: 자동 테스트

### START-05 자동 실행 설정을 바꾸지 못하면 알린다
- 조건: OS가 자동 실행 등록이나 해제를 거부한다(권한 없음 등)
- 동작: ⋯ 메뉴에서 `menu.autoStart`를 누른다
- 결과: 안내 줄에 `notice.autoStartFailed`("자동 실행 설정을 바꾸지 못했어요")를 보여 준다. 체크 표시는 누른 대로가 아니라 다시 읽은 실제 등록 상태를 보여 준다. 이 안내는 자동 실행 설정을 다시 바꾸는 데 성공하거나 위젯을 다시 켜면 사라진다
- 확인: 자동 테스트

### START-06 시작할 때 자동 실행·첫 설정 저장이 실패해도 위젯은 뜬다
- 조건: 시작할 때 OS 자동 실행 등록·경로 갱신이나 처음 실행의 `settings.json` 만들기가 실패한다(권한 없음, 디스크 문제 등)
- 동작: 위젯을 켠다
- 결과: 조용히 넘어가고 위젯은 평소처럼 뜬다. 안내 줄에도 아무것도 보여 주지 않는다
- 확인: 자동 테스트

### START-07 개발 빌드는 자동 실행을 건드리지 않는다
- 조건: 개발 모드(개발용 빌드)로 실행한다
- 결과: START-02·START-03의 자동 실행 단계(켜기, 경로 갱신)를 건너뛰어 개발용 실행 파일이 자동 실행에 등록되지 않는다. 처음 실행의 `settings.json` 만들기는 그대로 한다. ⋯ 메뉴로 직접 켜고 끄는 것(START-04)은 개발 빌드에서도 된다
- 확인: 자동 테스트

### START-08 ⋯ → 종료로 끝낸다
- 동작: ⋯ 메뉴에서 `menu.quit`("종료")를 누른다
- 결과: 창을 닫으면서 설정을 저장하고(WND-14) 프로세스가 끝난다. 할 일은 바꿀 때마다 저장하므로 따로 저장하지 않고, 아직 쓰는 중인 저장이 있으면 그것이 끝나기를 기다린다. 이 저장과 기다림은 3초를 넘기지 않는다. 3초 안에 끝나지 않으면 기다리지 않고 끝낸다(메뉴 막대 "종료"와 같다). 끝난 뒤에는 다시 실행하면 START-01의 "이미 떠 있음"으로 보지 않고 새로 뜬다
- 확인: 자동 테스트

### START-09 안내 줄은 한 번에 하나만 보여 준다
- 조건: 알릴 일이 여러 개 겹친다
- 결과: 안내 줄에는 우선순위가 가장 높은 것 하나만 보인다. 우선순위는 할 일 저장 실패(`notice.saveFailed`, "저장하지 못했어요. 다음 변경 때 다시 시도해요". `tasks.json`을 쓰지 못한 경우이고(변환용 백업 실패 포함), `settings.json` 저장 실패는 알리지 않는다) > 파일 문제(`notice.newerFile`, "새 버전에서 만든 파일이에요. 업데이트해 주세요" / `notice.backup`, "저장 파일에 문제가 있어 백업해 두었어요" 순) > 자동 실행 실패(`notice.autoStartFailed`) > 새 버전 안내(업데이트, UPD) 순이다. 위 안내가 사라지면 그다음 우선순위의 안내가 보인다. 예외로, `notice.newerFile`이 보이는 동안 새 버전이 있으면 그 안내 옆에 `update.action`("업데이트") 버튼도 함께 보인다(UPD-03). 업데이트하라고 알리면서 누를 것이 없으면 안 되기 때문이다. 그 버튼을 누르면 설치하는 동안은 `notice.newerFile` 대신 `update.installing`을 보여 준다(UPD-04). 받기나 설치에 실패하면 `notice.newerFile` 옆에 `update.failed`와 `update.action`을 함께 보여 주어 바로 다시 시도할 수 있게 한다(UPD-07). 파일은 여전히 새 버전에서 만든 것이므로 `notice.newerFile`은 사라지지 않는다. `update.failed`는 다음에 확인에 성공할 때까지 남고, 그때 새 버전이 여전히 있으면 `notice.newerFile` 옆에 `update.action`만 보이고, 없으면 둘 다 사라진다. 이렇게 안내를 함께 보여 문구가 길어지면 안내 줄은 용어의 정의대로 두 줄까지 줄바꿈된다
- 확인: 자동 테스트
